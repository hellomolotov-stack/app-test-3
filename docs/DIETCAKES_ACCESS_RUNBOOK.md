# Регламент работы с dietcakes.ru без повторных блокировок

Версия 1.0 · исследование 20 октября 2026 года · для Codex, Claude Code и ручной работы владельца

## Коротко

На сайте действительно активен **Loginizer 2.0.9** с защитой от перебора паролей. В его настройках: 3 неудачных входа → блокировка на 15 минут; 5 блокировок → продление на 24 часа; сброс счётчика попыток через 24 часа. Это прочитано в действующей админке, а не предположено по внешнему виду сайта. Назначение параметров сверено с [документацией Loginizer](https://loginizer.com/docs/configuration-and-settings/how-to-configure-brute-force-security/).

Однако **причина прежней недоступности всего сайта не установлена**. Loginizer защищает вход; его наличие само по себе не объясняет тайм-ауты главной страницы и каталога. Нужны журналы хостинга с временем события и исходящим IP.

Рабочий способ — использовать штатный доступ и устранить ложные срабатывания у владельца защиты. Этот документ не обещает отсутствие блокировок: реальные серверные лимиты пока неизвестны.

В исторической диагностике 16.10.2026 пользователь подтвердил, что без VPN сайт сразу открывался. Это подтверждает зависимость от VPN-маршрута/адреса, но не устанавливает конкретный механизм блокировки. В старой заметке проекта описаны два предполагаемых бана после частых запросов, выгрузки каталога и сохранений; серверных журналов к этой заметке нет. Утверждение из неё «curl 000 + сайт работает снаружи = бан IP» считать неподтверждённым: `000` означает, что HTTP-ответ не получен, а не отдельный HTTP-код блокировки.

## 2. Какой путь выбирать для изменения

| Задача | Основной путь |
| --- | --- |
| Текст, оформление, состав и поведение конструктора бокса | Рабочий репозиторий `/Users/maksmolotov/app-test-3`, файл `assets/dc/hiking-box.js`, штатный выпуск на Vercel в пределах разрешённой задачи |
| Слайдер и шторка бокса в приложении | Файлы приложения в том же рабочем репозитории; WordPress не нужен |
| Товары, цены, настройки магазина, сама запись WordPress | Существующая авторизованная сессия либо заранее настроенный официальный API с необходимыми правами |
| Массовый экспорт или много изменений WordPress | Отдельный план с оценкой числа запросов и согласованием допустимого режима у администратора/хостинга; сначала использовать имеющиеся локальные выгрузки |

По комментариям действующего `assets/dc/hiking-box.js`, страница `/hiking-intelligence` содержит контейнер и подключение `https://app-test-3-delta.vercel.app/assets/dc/hiking-box.js`. Поэтому обычную правку бокса не переносить в редактор WordPress. ID страницы из материалов проекта — **15624**; перед изменением самой записи сверить фактический адрес и текущий текст. Комментарий в коде не заменяет такую проверку.

## 3. Обязательный порядок для агента

1. **Прочитать этот документ.** Определить конкретную цель, файл/страницу и необходимость обращаться к WordPress. Сначала проверить локальный код и сохранённые материалы. Не открывать админку «на всякий случай».
2. **Подготовить правку локально.** Проверить актуальную рабочую копию, существующие изменения пользователя и diff; сохранить предыдущий вариант. Все мелкие изменения собрать в один пакет. Проверить код/макет локально до сохранения на сайте.
3. **Выбрать один канал работы.** Не запускать одновременно браузер, скрипт и другого агента для одной задачи в WordPress. Не менять VPN, прокси или сеть во время операции. Не считать IP браузера, терминала и облачного исполнителя одинаковым без проверки.
4. **Проверить доступ минимально.** Использовать уже открытую рабочую страницу, если она актуальна. Если проверка действительно нужна — одно обычное открытие нужной страницы. При тайм-ауте или ограничении перейти сразу к разделу 5; не продолжать проверки другими инструментами.
5. **Использовать штатную авторизацию.** Для интерфейса — существующую сессию. Если она истекла, прекратить автоматизацию входа и восстановить доступ штатно. После первой ошибки авторизации остановиться: не подбирать пароль и не проверять оставшиеся попытки. Для API — только заранее разрешённый и настроенный способ из раздела 4.
6. **Прочитать текущий объект один раз.** Перед записью сохранить резервную копию нужного содержимого и доступную метку версии/изменения. Проверить отсутствие параллельных правок. Если свежесть проверить нельзя или найден конфликт, запись отложить до его разрешения.
7. **Сохранить один раз.** В WordPress отправлять готовое изменение одной операцией. Если соединение оборвалось во время записи, её результат неизвестен: не повторять запись автоматически. Сначала выяснить состояние по правилам восстановления доступа.
8. **Проверить один раз и завершить.** Одна целевая проверка результата. При несовпадении определить причину по имеющимся данным; не запускать цикл «сохранить → обновить». Учитывать кеш браузера, PWA и WP Rocket. Глобальную очистку кеша и прогрев всего сайта не использовать как обычный способ проверки.
9. **Зафиксировать результат.** Записать что изменено, локальную версию/коммит, время, способ сохранения и результат проверки. Если сайт не удалось проверить — прямо указать это, не объявлять работу проверенной на продакшене.

### Собственные ограничения до выяснения лимитов хостинга

Это консервативная внутренняя политика, **не измеренные безопасные лимиты dietcakes**. Даже один запрос может попасть под правило защиты.

- Только одна инициированная агентом операция к dietcakes одновременно; никаких параллельных HTTP-запросов, сканеров и обхода каталога.
- Для прямых динамических HTTP/API-чтений — минимум 10 секунд между началами запросов; после записи — минимум 30 секунд перед проверкой. Самостоятельные повторы отключены (`retries=0`).
- Для обычной небольшой правки WordPress планировать максимум 5 явных динамических операций: проверка доступа при необходимости, чтение, проверка актуальности при необходимости, запись, проверка результата. Большая задача требует нового плана до начала запросов.
- Для браузера считать явные переходы и сохранения. Одна загрузка страницы сама вызывает множество фоновых запросов; этот бюджет не ограничивает их автоматически и не является гарантией. Не открывать несколько копий редактора, отключать функции магазина или менять Heartbeat ради соблюдения условного числа.
- Данные товаров брать из локального кеша; при необходимости — только известные ID и необходимые поля через поддерживаемый API. Никаких циклов по всему каталогу и автоматического перебора страниц.
- Внешние изображения, ассеты и результаты исследований сохранять локально и использовать повторно. Не обходить сайт повторно для каждого мелкого вопроса.

## 4. Штатный API для регулярной работы

Для длительной автоматизации предпочтителен отдельный пользователь с минимально достаточными правами и отзывным **WordPress Application Password**, работающий по HTTPS. Это проект настройки, а не уже выданный доступ. Пароль приложения наследует возможности пользователя; сам по себе он **не ограничивает доступ одной страницей 15624** и не отменяет WAF. Для ограничения одной страницей нужны соответствующая модель прав или специально спроектированный серверный endpoint. См. [WordPress: Application Passwords](https://developer.wordpress.org/advanced-administration/security/application-passwords/).

Не копировать cookies, пароли, Authorization и nonce в репозиторий, отчёты, скриншоты или журнал команд. Не получать nonce циклом. Браузерная cookie-авторизация REST требует корректного nonce; ошибка или истечение nonce не доказывает бан IP: [WordPress: REST authentication](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/).

Создание пользователя/секрета и изменение прав — отдельная настройка с разрешением владельца. Использовать существующий доступ, пока эта настройка не выполнена. Секреты хранить в предназначенном для них хранилище и передавать только штатному сервису по HTTPS, без вывода значения.

## 5. Когда немедленно остановиться

При первой ошибке авторизации, HTTP 403/429, неожиданном 415/503, странице проверки браузера/CAPTCHA или тайм-ауте остановить автоматические обращения к dietcakes. Если вместо ожидаемого JSON пришёл HTML, также остановиться. Не все эти ответы означают бан; до выяснения причины продолжать нельзя.

| Наблюдение | Что оно означает и что делать |
| --- | --- |
| Ошибка пароля / Loginizer сообщает о блокировке | Прекратить попытки входа; проверить правильность доступа и журнал Loginizer через владельца/администратора |
| HTTP 401 | Возможна ошибка учётных данных или выбранного способа авторизации. Не пробовать другие пароли автоматически |
| HTTP 403 | Возможны права WordPress, nonce, запрет WAF или иная проверка. Сохранить безопасный текст ошибки и ID события; не объявлять причиной конкретный плагин без доказательств |
| HTTP 429 | Ограничение частоты. Зафиксировать `Retry-After`, если есть; не возобновлять работу автоматически по таймеру |
| HTTP 503 или 415, HTML challenge | Возможны защита, технический сбой или неподдерживаемый формат. Код сам по себе не определяет поставщика защиты |
| DNS/TCP/TLS timeout, curl 000 | HTTP-ответа нет. Возможны сеть, VPN, сервер или блокировка адреса. Прекратить повторы; нужен разбор этапа сбоя и серверных логов |
| Тайм-аут после POST/сохранения | Изменение могло примениться. Повторная запись запрещена до выяснения результата |

После остановки: сообщить пользователю симптом и неизвестные обстоятельства, сохранить карточку инцидента, получить разбор администратора/хостинга. Одна контрольная проверка допустима после подтверждения восстановления или согласованного плана диагностики. Восстановление сети и проверка факта уже выполненной записи предшествуют любому повтору записи.

Не обходить остановку сменой IP/VPN-сервера, подменой поискового робота, обходом CAPTCHA, обращением к скрытому origin или кодированием содержимого для ухода от правила. Изменение сетевого маршрута для диагностики — отдельный согласованный тест, а не автоматическое продолжение заблокированной операции.

## 6. Как устранить причину надолго

1. **Получить журналы прежнего или нового инцидента.** Нужны время, исходящий IP именно исполнителя запроса, URL, метод, код и ID сработавшего правила. Проверить отдельно Loginizer, журналы веб-сервера и защиту хостинга. Сейчас доказательств для выбора конкретной серверной защиты нет.
2. **Если виноват Loginizer:** исправить источник неверных входов. Для согласованного постоянного административного IP можно рассмотреть точечный список разрешённых адресов. Он освобождает этот IP от ограничений Loginizer, но не от защиты хостинга: [официальная инструкция](https://loginizer.com/docs/configuration-and-settings/how-to-whitelist-an-ip-from-login/). Не добавлять общедоступный VPN или широкую подсеть. Это ослабление защиты для адреса и требует отдельного решения владельца; сейчас список не менялся.
3. **Если подтверждён WAF/ModSecurity:** попросить администратора/хостинг разобрать конкретное ложное срабатывание и предложить минимальное исключение для нужного правила/параметра/маршрута/метода, по возможности с ограничением источника и срока. Не отключать весь WAF. Доступность таких ограничений зависит от реальной системы.
4. **Если причина — VPN/сеть:** согласовать устойчивый рабочий маршрут. Не называть это устранением блокировки, пока причина не подтверждена. Изменения VPN и раздельного туннелирования выполнять отдельно, с сохранением прежних настроек и проверкой результата.
5. **Для регулярных изменений WordPress:** настроить минимальные права, официальный API и тестовую среду. Большие изменения сначала проверять там; на рабочий магазин переносить готовый результат.

Не устанавливать «антибан» плагины и не повышать лимиты наугад. Найденный Loginizer — реальный факт; ModSecurity пока только обоснованный кандидат для проверки у хостинга.

## 7. Карточка инцидента

```text
Задача:
Дата/время МСК и UTC:
Исполнитель: браузер / локальный скрипт / облачный сервис
Исходящий публичный IP этого исполнителя: известен / неизвестен
Сеть/VPN: состояние до ошибки, без последующего переключения
Метод + URL: без секретных query-параметров
Ответ: HTTP-код / тайм-аут на известном этапе / этап неизвестен
Текст ошибки: кратко, без cookies, токенов и персональных данных
Request ID / Ray ID / rule ID: если возвращён
Retry-After: если возвращён
Сколько явных операций было и за какое время:
Последняя запись: не выполнялась / подтверждена / результат неизвестен
Локальная резервная копия / версия изменения:
Автоматические обращения остановлены: да
Результат разбора администратора и основание возобновления:
```

Тела запросов и полные логи не прикладывать по умолчанию: они могут содержать секреты, данные покупателей и заказов. Перед передачей поддержке подготовить минимальный очищенный фрагмент и согласовать передачу приватных данных.
